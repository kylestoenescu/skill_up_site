1. Declaring variables: let, const, var

A declaration does two things: it creates a name, and it decides where that name exists. That second part is what trips people up, because let/const and the older var answer it differently.

A block is anything between curly braces — the body of an if, a loop, or a bare { }. let and const live only inside the block they were declared in. Watch what that means: 

let message = "outer";

{
  let message = "inner";
  console.log("inside the block:", message);
}

console.log("outside the block:", message);

Two separate variables that happen to share a name. The inner one is created when the block starts and is gone when it ends, so the outer one is untouched. Delete the word let from the inner line and it would stop being a declaration and become an assignment to the outer variable — printing inner both times.

const works the same way for scope, but adds one rule: you can't point the name at something else afterwards. That is not the same as the value being frozen, which is the most common misreading: 

const scores = [10, 20];

scores.push(30);          // fine — changing what the array contains
console.log(scores);

try {
  scores = [1, 2];        // not fine — repointing the name itself
} catch (err) {
  console.log("Error:", err.message);
}

const protects the binding, not the contents. The array is still mutable; you just can't make scores refer to a different array. This is why const is a sensible default: it says "this name means one thing throughout", which is true far more often than not, and reaching for let becomes a signal that something genuinely changes.

Now var, which is worth understanding mainly so you can recognise it in older code. It ignores blocks entirely and attaches to the whole surrounding function: 

function withVar() {
  if (true) {
    var x = "declared inside the if";
  }
  return x;                 // still visible out here
}

function withLet() {
  if (true) {
    let y = "declared inside the if";
  }
  try {
    return y;               // not visible — different scope
  } catch (err) {
    return "Error: " + err.message;
  }
}

console.log("var: ", withVar());
console.log("let: ", withLet());

var leaking out of the block is not a bug you can see until it bites. The rule of thumb is simple: use const by default, let when the value genuinely changes, and var never in new code.

2. The typeof null quirk

typeof tells you what kind of value you're holding. It is mostly predictable, and then there is one entry that is simply wrong: 

console.log(typeof "hello");
console.log(typeof 42);
console.log(typeof true);
console.log(typeof undefined);
console.log(typeof { a: 1 });
console.log(typeof [1, 2, 3]);
console.log(typeof null);      // the odd one out

null is its own primitive type, so "null" would be the sensible answer — but typeof null returns "object". This is a bug from the first version of JavaScript in 1995 that can never be fixed: too much existing code depends on the wrong answer, so correcting it would break the web.

Two practical consequences. First, typeof can't distinguish null from a real object. Second, typeof is also useless for telling an array from an object — both say "object". So when you actually need to check: 

const values = [null, { a: 1 }, [1, 2], "text", undefined];

values.forEach(function (value) {
  console.log(
    format(value),
    "| null?", value === null,
    "| array?", Array.isArray(value)
  );
});

function format(v) {
  return JSON.stringify(v) + " (typeof " + typeof v + ")";
}

Compare against null directly with ===, and use Array.isArray() for arrays. Note also that undefined and null are different things: undefined usually means "never set", while null usually means "deliberately empty".

3. JSON.stringify and JSON.parse

JSON is text. A JavaScript object lives in memory and can hold anything; JSON is a string format for sending that data somewhere else — an API, a file, localStorage. The two functions convert between them, in opposite directions: 

const user = { name: "Ada", age: 36, admin: true };

const text = JSON.stringify(user);
console.log("as text:  ", text);
console.log("its type: ", typeof text);

const back = JSON.parse(text);
console.log("parsed:   ", back);
console.log("age + 1:  ", back.age + 1);   // a real number again

Because JSON is a smaller format than JavaScript, some values have nowhere to go. stringify doesn't warn — it quietly drops them: 

const record = {
  name: "Ada",
  age: undefined,           // dropped entirely
  greet: function () {},    // dropped entirely
  joined: new Date(0),      // survives, but as a string
  score: null               // null is valid JSON, so it stays
};

console.log(JSON.stringify(record));

The date is the one to watch: it goes out as a string and comes back as a string, not a Date — a round trip through JSON is not guaranteed to give you back what you put in.

The other thing to know is how parse fails. It does not return undefined or null on bad input; it throws, which stops your code unless you catch it: 

function safeParse(text) {
  try {
    return JSON.parse(text);
  } catch (err) {
    console.log("could not parse:", err.message);
    return null;
  }
}

console.log(safeParse('{"ok": true}'));
console.log(safeParse("not json at all"));
console.log("still running");

Any time the text came from outside your program — a network response, a file, something a user pasted — wrap the parse in try/catch. Without it one malformed response takes the whole page down.

4. Closures

Skip the definition for a moment. Here is a real problem: you want a counter that hands out 1, 2, 3… and nothing else in the program can interfere with it. The obvious first attempt uses a variable outside the function: 

let count = 0;

function next() {
  count = count + 1;
  return count;
}

console.log(next());
console.log(next());

count = 900;               // anyone can do this
console.log(next());       // counter is now wrong

It counts, but count is out in the open. Any other code — a typo, a later feature, a colleague — can reach in and change it. So the natural fix is to move the variable inside the function, where nothing else can see it: 

function next() {
  let count = 0;           // now private…
  count = count + 1;
  return count;
}

console.log(next());
console.log(next());
console.log(next());       // stuck on 1 forever

Now it is private but useless. The variable is created fresh every call, so it resets to 0 before every increment. We seem to be stuck between "shared and vulnerable" and "private and forgetful".

The way out is to have two functions: an outer one that runs once to create the variable, and an inner one that runs many times and uses it. 

function makeCounter() {
  let count = 0;                 // created once, when makeCounter runs

  return function () {           // this function is returned, not called
    count = count + 1;
    return count;
  };
}

const next = makeCounter();      // runs the outer function once

console.log(next());
console.log(next());
console.log(next());

That is a closure. makeCounter finished and returned long before next() was ever called — yet count is still there. A function in JavaScript doesn't just remember its code; it keeps a reference to the scope it was created in. As long as the inner function is alive, count stays alive with it, and nothing outside can touch it because there is no name for it out there.

The consequence people miss: each call to the outer function makes a new scope, so counters made separately are genuinely separate. 

function makeCounter() {
  let count = 0;
  return function () {
    count = count + 1;
    return count;
  };
}

const a = makeCounter();
const b = makeCounter();

console.log("a:", a(), a(), a());
console.log("b:", b());            // b has its own count
console.log("a:", a());            // a carried on from where it was

Once you see it that way, the pattern generalises: the outer function is a factory that bakes a value in, and the inner function uses it forever. 

function makeGreeter(greeting) {
  return function (name) {
    return greeting + ", " + name + "!";
  };
}

const hello = makeGreeter("Hello");
const oi = makeGreeter("Oi");

console.log(hello("Ada"));
console.log(hello("Grace"));
console.log(oi("Ada"));

greeting was a parameter of a function that has already returned. It survives because the inner function closed over it. This is also, quietly, how a lot of JavaScript works — event handlers, callbacks and anything you pass to setTimeout all rely on closing over the surrounding scope.

A last one, because it connects back to section 1. This is the classic var loop bug, and it is really a closure question: 

console.log("with var:");
for (var i = 1; i <= 3; i++) {
  setTimeout(function () { console.log("  i =", i); }, 10);
}

console.log("with let:");
for (let j = 1; j <= 3; j++) {
  setTimeout(function () { console.log("  j =", j); }, 20);
}

var i is one variable for the whole loop, so all three callbacks close over the same i — and by the time they run, the loop has finished and left it at 4. let j creates a fresh binding each iteration, so each callback closes over its own copy. Same code shape, completely different result, and the difference is entirely about which scope was captured.

5. Promises and async/await

Start with the surprise, because everything else follows from it. JavaScript runs one thing at a time. Anything that has to wait — a network request, a timer — is handed off, and your code carries straight on: 

console.log("1. first line");

setTimeout(function () {
  console.log("3. inside setTimeout, 0ms");
}, 0);

console.log("2. last line");

0 milliseconds and it still runs last. "0ms" doesn't mean "now", it means "as soon as the current work is finished". Everything synchronous runs to completion first — then the queued callbacks. If you take one thing from this section, take that.

So how do you use a value that hasn't arrived yet? The old answer was to pass a function to be called later. That works, but it nests — here are three dependent steps: 

function getUser(id, callback) {
  setTimeout(function () { callback({ id: id, name: "Ada" }); }, 100);
}
function getOrders(user, callback) {
  setTimeout(function () { callback(["a", "b", "c"]); }, 100);
}
function getTotal(orders, callback) {
  setTimeout(function () { callback(orders.length * 25); }, 100);
}

getUser(1, function (user) {
  getOrders(user, function (orders) {
    getTotal(orders, function (total) {
      console.log(user.name + " spent " + total);
    });
  });
});

Three steps, three levels of indentation, and the actual result is buried at the bottom. Add error handling to each step and it roughly doubles. This shape has a name — "callback hell" — and it's what promises were introduced to fix.

A promise is an object representing a value that isn't ready yet. Instead of taking a callback, the function returns the promise, and you attach what happens next with .then(): 

function getUser(id) {
  return new Promise(function (resolve) {
    setTimeout(function () { resolve({ id: id, name: "Ada" }); }, 100);
  });
}
function getOrders(user) {
  return new Promise(function (resolve) {
    setTimeout(function () { resolve(["a", "b", "c"]); }, 100);
  });
}
function getTotal(orders) {
  return new Promise(function (resolve) {
    setTimeout(function () { resolve(orders.length * 25); }, 100);
  });
}

getUser(1)
  .then(function (user) {
    console.log("got user:", user.name);
    return getOrders(user);        // returning a promise chains it
  })
  .then(function (orders) {
    console.log("got orders:", orders.length);
    return getTotal(orders);
  })
  .then(function (total) {
    console.log("total:", total);
  });

The same three steps, but flat instead of nested. The trick is the return inside each .then(): returning a promise makes the next .then() wait for it. Forget that return and the chain stops waiting — one of the most common promise bugs.

async/await is a different syntax for exactly the same promises. await pauses the function until the promise settles and hands you the value directly: 

function delay(ms, value) {
  return new Promise(function (resolve) {
    setTimeout(function () { resolve(value); }, ms);
  });
}

async function run() {
  const user = await delay(100, { name: "Ada" });
  console.log("got user:", user.name);

  const orders = await delay(100, ["a", "b", "c"]);
  console.log("got orders:", orders.length);

  const total = await delay(100, orders.length * 25);
  console.log("total:", total);
}

run();
console.log("(this line runs before any of the above)");

It reads top to bottom like ordinary code, which is the whole point — but note the last line. await only pauses the function it is inside; the rest of the program keeps going. That's also why await is only allowed inside an async function.

Errors follow the same split. A promise that fails is rejected, caught with .catch() — or, with await, by ordinary try/catch: 

function mightFail(shouldFail) {
  return new Promise(function (resolve, reject) {
    setTimeout(function () {
      if (shouldFail) reject(new Error("server said no"));
      else resolve("all good");
    }, 100);
  });
}

mightFail(false).then(function (msg) { console.log(".then:", msg); });

mightFail(true).catch(function (err) { console.log(".catch:", err.message); });

async function withAwait() {
  try {
    await mightFail(true);
  } catch (err) {
    console.log("try/catch:", err.message);
  }
}
withAwait();

A rejected promise with no .catch() and no surrounding try/catch becomes an "unhandled rejection" — it won't crash the page, but the error goes to the browser console where you may never look. Always handle the failing branch.

Last one, and it is the most useful in practice. Two awaits in a row run one after the other, even when the tasks don't depend on each other. If they're independent, start them both and wait together: 

function delay(ms, value) {
  return new Promise(function (resolve) {
    setTimeout(function () { resolve(value); }, ms);
  });
}

async function oneAtATime() {
  const start = Date.now();
  const a = await delay(200, "a");
  const b = await delay(200, "b");
  console.log("sequential:", a + b, "took about", Date.now() - start, "ms");
}

async function together() {
  const start = Date.now();
  const both = await Promise.all([delay(200, "a"), delay(200, "b")]);
  console.log("Promise.all:", both.join(""), "took about", Date.now() - start, "ms");
}

oneAtATime();
together();

Roughly 400ms versus roughly 200ms for the same work. Promise.all starts everything immediately and resolves once all of them are done. Use sequential await only when a step genuinely needs the previous step's result — as in the user → orders → total chain above.

One more piece of ordering, since it comes up: promise callbacks jump the queue ahead of timers. Given a setTimeout(…, 0) and a Promise.resolve().then(…) registered together, the promise callback always runs first. Synchronous code, then promises, then timers.
